# The enforcement ladder — every model action surface, audited

**Status: AUDIT + BACKLOG.** Produced 2026-08-11 by a 4-agent adversarial audit answering the
operator's question: which failures can be made *inexpressible* (not guarded)?

## The ladder
- **R1 prompted** — instructions say don't. Ignorable. (This team deletes these.)
- **R2 nudged** — tool results push back; a persistent model gets through.
- **R3 checked** — the wrong action is rejected at call time.
- **R4 capability-absent** — the failure is inexpressible: no tool, no data, no credential.
- **R5 correct-by-construction** — the only executable path IS the correct behavior.

Rule: every incident fix moves its class UP the ladder; R1 fixes are banned. The residual
column marks what no rung can close: **judgment** — her product. You cannot make bad judgment
inexpressible without deleting the judgment; that residual is carried by model quality, small
blast radius, reversibility, and the regression ratchet — never by more prompt text.

Three defects this audit found in the overhaul (drafts eaten by dead wakes; delivery sentinels
treated as posted; §5.5 disarmed inside mixed wakes) were fixed in the same commit that adds
this file. The rest is the promotion backlog, worst-rung first.

## External write tools — the signing identity (catalog.ts:107-116; LINEAR_API_KEY in the daemon env, /home/exedev/earshot/.env)

- **failures:** The Linear credential is a personal API key, so every mutation attributes to its creator: 2026-08-10, T-261 posted ~8 directive @-mention comments to four teammates under Noah's name ("spamming linear as me"). Personal keys have no per-request attribution override. No tool-level gating can fix this — the credential speaks as the wrong person. It is the same class of harm CLAUDE.md's "nothing mechanical to Slack / harness never speaks" rule prevents on the Slack side, unprotected on every other write surface. GITHUB_TOKEN and the Notion token need the same audit.
- **rung:** R0 — nothing in the code can detect it; it is a property of the secret → ceiling R4 — literally "the credential can't sign as the wrong identity" · residual: none
- **promotion:** A dedicated Linear seat for the agent, or a Linear OAuth app with actor=application ("posted by app"). Swap the value in the daemon .env and restart — hot-reload does not cover .env. Repeat the audit for GitHub and Notion.
- **cost:** One Linear seat (money) + OAuth app setup. Zero code change in this repo; the failure mode is then gone permanently for every future tool call and every future task.

## The desk — free-form workspace files as a second, unmanaged memory store (src/turn-runner/soul.ts:188-195, over the shared cwd of the row above)

- **failures:** The soul instructs her to keep durable notes in the working directory ("Anything you did not write down is gone"), and codex's workspace-write sandbox lets her. Those notes are memory that the memory system does not govern: §8.3 retraction cannot reach them, §8.4 inspection ("what have you remembered?") does not see them, §8.6 tier/budget does not bound them, §8.7 search does not index them, and with one shared cwd they are readable by every identity's session and by every worker. A corrected fact survives in desk notes after memory_retract has done its job — the same stale-fact-recited failure, in a channel with no retract path at all.
- **rung:** none (unmanaged) → ceiling R4 for the isolation half; R3 at best for the retraction half · residual: judgment
- **promotion:** Isolation: per-identity workspace (identical mechanism to the row above) removes cross-identity readability outright. Retraction: the only structural fix is to stop the desk being durable — treat the workspace as scratch that is recreated per wake, leaving memory_items (retractable, searchable, inspectable, budgeted) as the sole persistence. That is a product decision, not a bug fix: it trades the notebook the soul promises for a memory store where "forget that" is total.
- **cost:** Wiping the desk costs the deliberate cross-wake continuity the soul is built around (working files, scratch analyses, SUPABASE.md-style local notes). Keeping the desk costs a permanent hole in §8.3/§8.4.

## Memory as a secret sink — §10.6 (src/turn-runner/toolset.ts:507-516 → src/ledger/memory.ts:76-84 → src/service.ts:1013)

- **failures:** memory_write accepts arbitrary content with no screening. A token pasted in chat, or a DSN/row returned by db_read or ops_read, can be written to core, at which point it is (a) persisted in the ledger forever, (b) written to AGENTS.md on disk, and (c) injected into every subsequent turn's context — §10.6 says secrets are "never included in turn context, audit records, or posted messages", and from core it is one quote away from a reply. src/log.ts:22 redacts by key name for logs only; nothing guards memory.
- **rung:** none → ceiling R3 · residual: mechanical
- **promotion:** Pattern-reject at the write site (memory.ts writeMemory, so both the tool and any future caller are covered): refuse content matching credential shapes — `xox[baprs]-`, `sk-[A-Za-z0-9]{20,}`, `ghp_`/`github_pat_`, `AKIA[0-9A-Z]{16}`, `-----BEGIN [A-Z ]*PRIVATE KEY`, `://[^/\s]+:[^@\s]+@` — with an output telling her to record the reference, not the value. R4 is not available: a secret is just a string, so it cannot be made unwritable, only unrecognized-shape-free.
- **cost:** A legitimate fact that quotes a token-shaped string is refused (rare, and the refusal is recoverable in-turn).

## delivery-result handling — sentinel message ids crossing the wrapper boundary (src/service.ts:334-341 returns 'undelivered', :670 returns 'already-sent-this-wake'; consumed unconditionally at src/turn-runner/toolset.ts:321-324)

- **failures:** replyTool treats every return from ctx.postMessage as success: it tells the model "posted" after deliverPost exhausted five attempts and nothing landed, pushes a `posted` effect (which also arms the retry loop's effects-nonempty guard at service.ts:818, preventing a retry of a wake that in fact said nothing), and calls recordPostedThread → engage(db, …, anchor.threadRootId ?? result.messageId) at :97 — so a failed TOP-LEVEL post mints a conversation row keyed thread_root_id='undelivered'. The same sentinel lands in checklist's ref.messageId (:481) and becomes the target of every subsequent chat.update.
- **rung:** R1/none — nothing rejects the sentinel; it is a plain string that flows everywhere a real message id flows. → ceiling R5 · residual: none
- **promotion:** Type the boundary: postMessage returns a discriminated result ({posted, messageId} | {duplicate} | {undelivered}) instead of {messageId: string}. Then "treat a non-delivery as posted" does not typecheck, the engage/attention-close/answered bookkeeping is unreachable on a non-delivery (the service closure already gets this right at :680-683 — the leak is toolset.ts's own unconditional recordPostedThread), and the model is told the truth so it can react.
- **cost:** Three call sites, no behavior loss, no latency.

## speech volume / chattiness — how much a woken turn says (soul.ts:15, :75-81, :150, :216-217; no code enforcement anywhere in the slice)

- **failures:** Receipt inflation (2026-07-09), the 9:1 reply:react ratio flagged in the M19 stance. Nothing bounds how many reply calls a wake makes, and nothing stops the same words going into two conversations in one wake (recordAct's act_key includes venue and thread, conversations.ts:384, so a cross-post of identical text inserts twice cleanly).
- **rung:** R1 for volume (soul text only). Note the real control already shipped one layer up and is R3: the ear gates whether she WAKES at all (service.ts:416-555), out-stance conversations withhold their observed chatter from delivery (conversations.ts:276), and identical worker reports no longer force a wake (service.ts:950-967). → ceiling R3, and only for the mechanical sliver · residual: judgment
- **promotion:** The only defensible mechanical piece is the duplicate check: bounce identical text posted into a second conversation within one wake, and identical text into the same conversation across a recency window (the cross-wake act check above covers both). A per-wake reply cap is the wrong shape and should not be built — it breaks the multi-conversation wake that the collapse exists to enable, and this team has ruled out engagement quotas on principle ("an emoji is a message").
- **cost:** Near zero for the duplicate bounce. A cap would cost the ability to answer three conversations in one wake, which is a capability loss the design cannot absorb.

## The open-task set the mind reads — task_query / ledgerView (ledger/tasks.ts:166-174; toolset.ts:252-256)

- **failures:** ledgerView returns EVERY non-terminal task with its full steering-appended spec — no cap, no age filter, parked included. Live: ~20 July zombie tasks (T-33 open since Jul 19) and task_query returning ~62KB into a turn. Nothing reconciles a room-level stop with the task born from that thread: 2026-08-10, Noah's "stop" in Slack did not touch T-261; the only kill switch that worked was pulling the API key off the VM. So the mind pays context for work nobody will resume, and a runaway task's brake is a human noticing.
- **rung:** R1/R2 — hygiene is left to the model, which does not do it → ceiling R3 for the size; R5 for the stop-linkage · residual: judgment
- **promotion:** (i) Bound the view: cap open rows, truncate specs, and put long-parked tasks behind an explicit includeParked flag — parked already means "nobody is coming" (§6.1). (ii) Link stance to tasks: step_back already closes a conversation's attention items (toolset.ts:708-719); make it also surface the tasks homed to that thread into the wake, so leaving a conversation and abandoning its work are one decision. The R5 form derives a task's liveness from its home conversation's stance and last human contact rather than letting it live until someone remembers to cancel.
- **cost:** (i) trivial. (ii) design care — surface-and-ask rather than auto-cancel, or in-flight work someone still wants gets killed.

## Ear verdict tool — naming WHICH conversation a judgment lands on (src/service.ts:428-485; schema at :441-442; guards at :454, :459)

- **failures:** venueId is OPTIONAL in the inputSchema and both durable writes are guarded by `if (a.venueId)`. A hold with no target returns `{success:true, output:"noted"}` and writes nothing — the exact discarded-hold class from 2026-08-10, re-opened at the tool boundary. This is not hypothetical: the canonical hold test (test/ear.test.ts:88) calls `verdict({decision:"hold", why:"teammates comparing lunch orders"})` with no venueId, and asserts only that the LINES ride the next wake — the why is dropped and nothing notices. A targetless `wake` is worse: needWake flips (service.ts:456) but recordWakeWhy is skipped, so (a) the why is lost, (b) the wake intent exists only in RAM — a crash before service.ts:548 loses it, and for an 'out' conversation hasUndelivered (conversations.ts:306-319) returns false because OUT_STANCE_EXCEPTIONS needs a non-null wake_why, so the boot re-wake at service.ts:173 never fires and the escalation is silent forever. Conversely a PRESENT-but-wrong pair is unchecked: recordHold/recordWakeWhy call ensureConversation (conversations.ts:180, 190), so a cheap-tier typo mints a phantom conversation row, and a wake_why on a mistyped key punches straight through a durable step-back via OUT_STANCE_EXCEPTIONS (conversations.ts:276). Unlike `reply`, which pairs-checks venue↔thread (toolset.ts:287-292), the verdict tool checks nothing.
- **rung:** R1/R2 — the ear soul says "one verdict per conversation" (ear-soul.ts) and the tool description names the fields; the harness accepts anything, including nothing, and reports success. → ceiling R4 · residual: judgment
- **promotion:** Bind the target to the pass instead of accepting it as free text. runEarPass already holds `convos` (service.ts:423); emit ONE verdict tool per rendered conversation, each closed over its own {venueId, threadRootId} (name them from the card, e.g. `verdict_C1_thread_1700.0`, with the card header carrying the same label). Then decision+why are the only arguments, a targetless verdict cannot be constructed, and a verdict about a conversation this pass did not read has no tool to call — the failure is inexpressible rather than caught. Floor if the tool-count is unacceptable: keep one tool, make `conversation` required with `enum: [...keys of this pass]` AND validate server-side against the map (R3 — wrong target fails, empty target impossible). Cap/page the pass at K conversations (unjudgedConversations already takes limit=200) so the tool list stays bounded. close_ask/reopen_ask keep their itemId form but see the attention-scope row below.
- **cost:** K tool specs per ear pass instead of 1 (K is normally 1-5; needs an explicit page size where today there is an implicit 200). Slightly longer tool list in the ear's context. No capability loss — the ear cannot usefully judge a conversation it was not shown, and the escalate-into-a-room-she-left path survives (that conversation IS rendered: unjudgedConversations deliberately omits the out-stance filter, conversations.ts:324-336). No latency cost.

## Core-memory injection rendering — the "What you know" section (src/turn-runner/soul.ts:239-248, fed by service.ts:981-987 via coreWithinBudget)

- **failures:** Each core fact renders as a bare bullet: `- ${f}` (soul.ts:247). No last_confirmed_at, no provenance, no tier label. A fact last confirmed six months ago is typographically identical to one written this morning, so the model cannot apply the soul's own "a fact keeps the strength it arrived with" rule (soul.ts:99-103) — it has no strength to read. provenance is stored (memory_items.provenance, schema.sql:97) but optional at write (memory.ts:81 `params.provenance ?? []`, and memory_write's inputSchema doesn't require it, toolset.ts:500-505) and never rendered anywhere. This is the recitation half of "stale memory as live fact".
- **rung:** R1 (soul prose asks for strength-preservation; the channel carries no strength) → ceiling R5 for the rendering, R3 for the write · residual: mechanical
- **promotion:** Render from the MemoryItem, not from `facts: string[]`: `- (as of 2026-07-14, from <permalink|jo in #eng>) the export path is mobile-only`. Change composeInstructions' knowledge param (soul.ts:232) to take items, so a fact without its as-of date is unrepresentable in the injected doc. Pair with R3 at the write: make provenance required in memory_write's inputSchema and enforce `CHECK (json_array_length(provenance) > 0)` on memory_items, so an unsourced fact cannot enter core.
- **cost:** ~25-40 chars per item against memory.coreCharBudget (fewer facts fit; the overflow note at soul.ts:245 already pushes curation). Required-provenance rejects writes where she has no source — which is the point, but it will bounce some genuine writes until she habitually passes the message ts.

## Identity isolation of the INJECTION channel and workspace — one AGENTS.md, one cwd, all identities (src/service.ts:977-1015, esp. :981-987 and :1013; sessions start there at :784-793 and :882; ear equivalent at :404-409 + src/turn-runner/ear-soul.ts:44-53)

- **failures:** refreshSoul loops over every identity in policy and concatenates all of their personas, all of their core facts, all of their venue_instructions and all of their tool digests into a single AGENTS.md written to this.d.cwd — which is the cwd every identity's resident wake and every worker starts codex in. §7.1 requires that eng's facts be "unavailable — not merely unmentioned" to sales, enforced "at the storage and tool-brokering layers, not by prompt instruction"; today the only thing separating them is the `## What you know (as eng)` heading, i.e. prompt instruction, the one mechanism §7.1 names as insufficient. Latent while the deploy runs one identity, but it is the multi-identity shape the SPEC sells, and the ear's soul has the same all-identities concatenation.
- **rung:** R1 → ceiling R4 · residual: mechanical
- **promotion:** Per-identity workspace: `${cwd}/${identityId}` (and `${earCwd}/${identityId}`), created at boot, with composeInstructions/composeEarInstructions taking ONE identity's knowledge instead of an array (soul.ts:230-235, ear-soul.ts:44). Each session then starts in a directory whose AGENTS.md contains only its own identity's facts, and codex's workspace-write sandbox (src/turn-runner/types.ts:22) does not hand it a sibling path. The ear already proves the split-workspace pattern (service.ts:386).
- **cost:** N workspace dirs to create and keep codex-trusted; one AGENTS.md write per identity per refresh instead of one global; deploy/DEPLOY.md gains a note. No capability loss — sharing context across venues is still the operator's venue_ids mechanism (§7.2), which is the intended sharing lever.

## Harness vocabulary reaching the room — venue instructions and denial strings (src/turn-runner/soul.ts:256; src/turn-runner/toolset.ts:124, :130-141, :284, :290, :308)

- **failures:** Live incident: model-facing text gets parroted into Slack. Venue instructions render verbatim into AGENTS.md and come back out in replies; denial outputs literally contain `not_available_for_turn_kind`, `interactive_consequential_denied`, `posting_scope_violation`, `requires_confirmation`. The current mitigation is to write those strings in room-safe language and append "never say this in the room" coaching (toolset.ts:133, :139) — R1 by this team's own standard, sitting inside an R2 tool result. Task IDs are the same shape of failure: soul.ts:69-71 forbids putting `T-42` in a message, and nothing checks.
- **rung:** R1 (phrasing discipline) over R2 (the bounce text itself) → ceiling R3 · residual: judgment
- **promotion:** Every word the room hears passes through exactly one function — replyTool's run (toolset.ts:275-325), before postMessage/bufferReply. Screen the text there: reject a post containing a harness token (`not_available_for_turn_kind`, `interactive_consequential_denied`, `posting_scope_violation`, `requires_confirmation`, a leading `denied:`), a ledger task id (`/\bT-\d+\b/`), or a verbatim N-word span of this identity's venue_instructions, and return her own text back as the tool result to rewrite. The bounce is a tool result, not a post, so §6.1 ("the harness never speaks") holds. R4 is unreachable here: you cannot make the concept inexpressible without also stopping her explaining a real limitation in her own words, which is the behavior the soul wants.
- **cost:** One retry round-trip on a hit; false positives when a human genuinely typed `T-4128` in the thread and she quotes it back (narrow the id pattern to the ledger's own `nextTaskId` format to shrink this).

## step_back — the presence change (src/turn-runner/toolset.ts:695-720; write at src/ledger/conversations.ts:76-85)

- **failures:** Weakest addressing in the slice: coordinates are required (:711) but there is no venuesForThread cross-check (which reply has at :287-292) and no checkPostingScope call at all. A mispaired or typo'd (venue, thread) goes through stepBack → ensureConversation + UPDATE, which CREATES the row and marks it 'out'. Result: the conversation she meant to leave stays engaged and keeps waking her, she is told "stepped back — a mention brings you back in", and a phantom 'out' row now sits ready to suppress observed traffic if that pair ever becomes real. It also silently drops attention debts for the phantom thread (:715). She can write an 'out' row for a venue the identity does not serve.
- **rung:** R2 — the wrong action succeeds and reports success. → ceiling R4 · residual: judgment
- **promotion:** Same conversation-ref argument as reply, plus make the write an UPDATE against an existing row (0 changes → error) instead of ensureConversation-then-UPDATE. Naming a conversation the wake never read, or a pair that has never existed, becomes unrepresentable rather than silently effective-elsewhere.
- **cost:** She can no longer pre-emptively step back from a conversation she has not been shown — arguably correct. A few lines.

## outbound retry — deliverPost (src/adapter/outbound.ts:23-43; only caller src/service.ts:335-340)

- **failures:** The classic duplicate: the post succeeded but the client saw a timeout, so the retry posts it again. The module documents this honestly at :4-7 and provides the mitigation hook (`checkAlreadyPosted`, :16, :31-34) — and no call site wires it. service.ts:335-340 passes maxAttempts/backoff/onExhausted only. Exhaustion falls through to an operator log line, which is correct under "the harness never speaks".
- **rung:** R2 — retries blind; the correction hook exists but is inert. → ceiling R3 · residual: mechanical
- **promotion:** Wire checkAlreadyPosted to a conversations.history lookup over (venue, thread, since-attempt-start, bot principal, text) before each retry, so a post that actually landed is detected and the retry is rejected at the delivery boundary rather than duplicating. R4/R5 is not purchasable: Slack chat.postMessage has no idempotency key, so "a duplicate is inexpressible" cannot be bought at this surface.
- **cost:** One extra API call per retry, only on the failure path; needs history read scope on the bot token; a small amount of matching logic (text equality within a time window).

## task_steer / task_cancel — task addressing by model-supplied id (toolset.ts:194-225; ledger/tasks.ts:176-180, 487-508)

- **failures:** `requireTask(db, taskId)` looks up by id alone; no call site on the steer/cancel/confirm path scopes by identity. Task ids are `T-1…T-n` and deliberately chat-visible (§4.2), so another identity's ids are observable, not opaque. §7.4 is explicit that the harness MUST make cross-identity reach impossible ("the data is not reachable by the turn's tools") — memoryRetractTool does exactly that ownership check for opaque UUIDs (toolset.ts:528, with a comment saying isolation must hold regardless of guessability), and the task path does not. Separately: guidance appends to `tasks.spec` forever (tasks.ts:509-512), so a long-lived task's spec grows without bound and rides every worker turn-1 prompt (service.ts:895-900).
- **rung:** R2 — a wrong-identity steer/cancel succeeds silently → ceiling R4 for the isolation (the row is unreachable, not merely rejected) · residual: none
- **promotion:** `requireTaskFor(db, identityId, taskId)` = `WHERE id = ? AND identity_id = ?`, used by task_steer/task_cancel/task_confirm/resolveConfirmation; a foreign task returns not_found, indistinguishable from nonexistent. Separately, cap spec amendments (bounded amendment list rather than unbounded concatenation).
- **cost:** None. One WHERE clause per call site.

## task_confirm — resolving a human's approve/deny (toolset.ts:235-242; policy/broker.ts:150-152; ledger/tasks.ts:620-659)

- **failures:** §10.2 requires "the model cannot fabricate a confirmation: eligibility and resolution are harness-verified ledger state, not turn context." Today the model passes `{taskId, approve}` and cites nothing; the only harness check is that the wake's batch-default principal (homeMsg's author, service.ts:664) is non-guest — and `principalOf` hardcodes `isGuest: false` for every principal (service.ts:322-327), so the guest gate is inert in production. No link exists between the approval and any human utterance. A wake that believes "kate said go ahead" produces a real, audit-logged approval attributed to whoever happened to speak last — the 2026-08-10 strong-and-wrong failure shape (acting on a belief no message supports) aimed at the consequential-action gate.
- **rung:** R2 dressed as R3 — the choke-point check exists (broker.ts:150) but checks the wrong principal, and its one discriminator is inert → ceiling R3, with R5 attribution · residual: judgment
- **promotion:** `task_confirm{taskId, approve, venueId, ts}` — the message carrying the go-ahead. Harness verifies (venueId, ts) is a delivered message of this wake, resolves the principal from that row rather than a batch default, applies §10.4 eligibility to that principal, and stores resolving_event_id in the resolution; UNIQUE(task_id, action_ref, resolving_event_id) makes double-resolution unrepresentable. Also wire real guest metadata (the users.info call already documented as a follow-up at service.ts:323-326).
- **cost:** One required arg — the model must point at the approval. An approval relayed out-of-band can no longer be entered, which is the intent. Guest metadata needs one Slack API call.

## Executing the confirmed action after approval — the actionRef binding (unimplemented; policy/broker.ts:122-130, ledger/tasks.ts:620-659, service.ts:895-900)

- **failures:** `resolution.approved` is written (tasks.ts:631,650) and read by nothing — `grep -rn approved src/` returns three hits, all writes. `actionClassDecision` never consults the task's pending_confirmation. So the approved path is a livelock: approve → revive to open → dispatch → a FRESH execution whose turn-1 prompt carries only the spec (service.ts:895-900, so the worker isn't even told it was approved) → it re-attempts the write → requires_confirmation again → waiting(human) again → nudge → park. An approved consequential action can never execute; §10.2's "Denied → MUST NOT perform it" holds only by accident, because approval is equally blocked. No test covers the post-approval call (test/toolset.test.ts:388-410 stops at the request).
- **rung:** R2 — the flow terminates in a loop; the denial is enforced only as a side effect of the approval being broken too → ceiling R5 · residual: judgment
- **promotion:** Make the approval a single-use capability token in the ledger: actionRef = hash of (tool, canonicalized args); on an execution_step call the broker allows iff a pending_confirmation on ctx.taskId matches that hash, `resolution.approved === true`, and the resolution belongs to the current execution (§10.2's "expire when the consuming execution ends") — marking it consumed in the same transaction as the call's audit row. The approved call becomes the only executable path for that exact argument set; a denied one has no token; a different action cannot reuse one because the hash is the key; replay is unrepresentable. Deliver the resolution into the resumed worker's prompt as state, not instruction.
- **cost:** Real work: canonical-args hashing, consumed_at on the confirmation, execution-scoped expiry, tests. No latency change, no capability loss.

## set_wake — self-scheduling yield (toolset.ts:372-379; ledger/tasks.ts:201-203, 333-338; ledger/timers.ts:27-30, 53-58; ledger/scheduler.ts:57-62)

- **failures:** `wakeAt` is an unvalidated model string stored verbatim into BOTH `tasks.wake_at` and the timer's `due_at`, then compared as a string (`due_at <= ?`, timers.ts:56). "tomorrow" or "2026-08-12 09:00" sorts after any ISO now and never fires — the task waits forever with a plausible-looking wake_at. No future check (a past value fires instantly → redispatch churn) and no horizon clamp. Worse: scheduleTimer is INSERT OR IGNORE on id `${taskId}:task_wake:${dueAt}` (tasks.ts:202); a task that ever yields twice to the same wakeAt string (a fixed timestamp in the spec, a redispatched attempt recomputing the same value) collides with the already-fired row, the insert is dropped, and tasks.wake_at then claims a wake that no timer will deliver. A precise mechanical generator of the ~20 July zombie tasks still in the ledger.
- **rung:** R2 → ceiling R5 for the skew, R3 for the value · residual: none
- **promotion:** (i) Validate at the tool boundary: parse to a Date, require finite and > now, clamp to a max horizon, re-serialize to canonical ISO — the ledger only ever stores harness-normalized timestamps. (ii) Kill the second source of truth: have the scheduler pass promote `tasks WHERE status='waiting' AND waiting_on='timer' AND wake_at <= now` directly, instead of depending on a timer row existing. wake_at then IS the schedule and drift between the two is unrepresentable — the same move the conversations watermarks just made.
- **cost:** One scheduler query replaces applyTaskWake; timers keep nudge/park (or get the same treatment). No migration needed — the columns exist. Small.

## task_complete / task_fail — the terminal report (toolset.ts:394-419; ledger/schema.sql:41; consumed at service.ts:935-941)

- **failures:** The report is unconstrained free text and is the ONLY thing that reaches the mind, who then speaks it to the room in her own voice. `terminal_report` has no NOT NULL or length CHECK for terminal statuses, so `task_complete{report:""}` satisfies §6.1's "no task may end without a ledger report" on paper. Nothing ties the report to what happened: external calls record no ledger effects at all (toolset.ts:636-637 says so explicitly), so a worker that did nothing and one that filed three tickets produce indistinguishable handoffs. The 2026-08-10 Linear spam is the mirror image — the real effects were 8 @-mention comments; the report was whatever the worker chose to say about them.
- **rung:** R2 → ceiling R3 for non-emptiness, R5 for receipts · residual: judgment
- **promotion:** (i) Partial CHECK in schema: terminal statuses require a non-empty trimmed terminal_report — the invariants-in-the-schema pattern CLAUDE.md #3 asks for. (ii) Compose the handoff the mind reads from ledger state: the model's report text PLUS the execution's recorded outward calls (tool, target ids). Not an instruction to "include receipts" — the receipts are joined in at delivery, so an under-reported action is still visible to the mind.
- **cost:** (i) a migration and one CHECK. (ii) requires outward calls to write ledger rows, which they currently never do — a real addition, but the same row that S12's durable dedupe needs. Moderate.

## task_ask — yielding on a blocking question (toolset.ts:430-438; relayed at service.ts:935-941)

- **failures:** The transition to waiting(human) fires whether or not any human is ever asked. §6.1 says the transition "presumes the yielding turn asked its question in-thread itself" — post-Collapse that premise is false: workers cannot post (broker.ts:93), the asking is now the mind's on a later wake, and nothing checks she relayed it. If workers must keep writing, the weaker R3 version is forcing tier='recent' at the write site for turnKind === 'execution_step' rather than trusting the argument.

## Out-stance delivery gating — the OUT_STANCE_EXCEPTIONS predicate (src/ledger/conversations.ts:276) used by pendingConversations (:286) and hasUndelivered (:314); stance writes at engage (:64-72) and stepBack (:76-85)

- **failures:** The gate itself is strong: the predicate lives inside the delivery SQL, so "observed chatter from a room she left reaches a wake" is not reachable through the delivery path, and the two readers share one constant so the wake-loop and the boot-wake can't disagree. Two real weaknesses. (1) The predicate is a TypeScript string spliced into queries, not a schema object — a future reader that writes its own SELECT over events silently loses the gate; nothing in the schema enforces it. (2) engage (:66) sets `stance_why = NULL`: a mention destroys the record of WHY she left. The 2026-08-10 lesson was that a decision-maker's own recorded judgment must survive to the next reader; here her most deliberate judgment ("the humans have this") is the one thing overwritten, so a post-re-engage wake cannot render "she stepped out at T because X, then was pulled back in". The step_back why also has no history — a second step_back overwrites the first, unlike holds which deliberately keep four (conversations.ts:20).
- **rung:** R4/R5 for the gate (the only executable delivery path carries the predicate); R2 for the durability of her stance reasoning (a single nullable column, last-write-wins, nulled on re-engage). → ceiling R5 · residual: judgment
- **promotion:** (1) Move the predicate into the schema as a view — `CREATE VIEW deliverable_events AS SELECT e.* FROM events e LEFT JOIN conversations c … WHERE e.kind IN (…) AND <out-stance exceptions>` — and have pendingConversations/hasUndelivered select from it. A reader physically cannot forget a WHERE clause that isn't in its query. (2) Make stance append-only: `stance_events(identity_id, venue_id, thread_root_id, stance, why, at)` with current stance derived (latest row) — matching the audit table's own append-only discipline (schema.sql:152-156). Then "her recorded why was destroyed" is unrepresentable, and the renderer can show the arc instead of a snapshot.
- **cost:** A view plus a table and migration; stanceOf becomes a `ORDER BY at DESC LIMIT 1` read (indexed, sub-ms). No capability loss. The escalation exception (wake_why punching through 'out') stays exactly as designed — its soundness depends entirely on the verdict-targeting promotion above.

## Hold / wake_why lifecycle across delivery — consumeJudgment (src/ledger/conversations.ts:202-219, reset at :213) vs the wake's commit (src/service.ts:843) and the ear's writes (:454, :459)

- **failures:** The single-threaded invariant is genuinely correct-by-construction — one transaction takes messages and judgment together, so "a wake got the messages without the reads" is unrepresentable. But the judgment is a SCALAR ON THE ROW with no idea which messages it described, and the ear and the wake are not mutually exclusive (independent guards: earRunning service.ts:138, residentRunning service.ts:130; nothing serializes them, and both are minutes-long model turns). Two live-shaped races follow. (A) Ear pass in flight, a mention arrives, scheduleWake(0) (service.ts:305) runs the wake to completion; the wake's finally consumes and zeroes the row (conversations.ts:213 resets holds/hold_whys/wake_why UNCONDITIONALLY, not by watermark); the ear's verdict then lands recordHold on the emptied row. That hold describes an already-delivered stretch and will render on a FUTURE wake as `the ear held it 1x: "..."` / `first read: ...` (renderConversation, conversations.ts:546-551) — a stale read presented as a live fact, which is precisely the 2026-08-10 strong-and-wrong shape. (B) The mirror: messages arrive mid-wake, the ear judges and holds them, and the wake's finally zeroes the row even though deliveredRowid stops short of those rows — a discarded hold for UNDELIVERED messages, the 2026-08-10 primary defect, structurally re-opened. Same root cause strands judgment on rehome (conversations.ts:131-155): holds only move with the root when it was the surface's SOLE undelivered message, otherwise they stay on the surface row and get consumed by an unrelated surface delivery.
- **rung:** R5 for the sequential case (delivery+judgment in one transaction, conversations.ts:204-217); effectively R2/broken under concurrency, because the representation cannot say WHICH messages a hold judged. → ceiling R5 · residual: none
- **promotion:** Key judgment to the message span it judged, not to the conversation row. A `conversation_judgments(identity_id, venue_id, thread_root_id, kind CHECK IN ('hold','wake_why'), why, from_rowid, to_rowid, at)` table written by recordHold/recordWakeWhy with the span the ear actually read (runEarPass already has it: c.messages[0].rowid .. c.messages.at(-1).rowid). consumeJudgment then deletes/returns only rows with `to_rowid <= deliveredRowid` and leaves the rest standing. Every named failure dies structurally: race (A) leaves a hold whose span is already below the watermark and is dropped at read time rather than rendered; race (B) leaves a hold above the watermark that survives to the wake that actually delivers those rows; rehome carries judgment because the span travels with the rowids, deleting the sole-undelivered-message special case (conversations.ts:131-155) outright. HOLD_WHY_KEEP (conversations.ts:20) becomes an ORDER BY … LIMIT instead of a json_remove dance.
- **cost:** One migration + table; recordHold/recordWakeWhy/consumeJudgment/getConversationJudgment become row reads instead of column reads; the renderer joins. ~60 lines net, most of it deleting the json_insert/json_remove expression and the rehome carry-over branch. No capability loss, no latency, no new service.

## Audit append-only + mutation/audit atomicity (src/ledger/schema.sql:141-156, src/ledger/db.ts:62-63 and :279-291, src/ledger/audit.ts:20-27, src/ledger/memory.ts:78-82/:96-101/:133-135)

- **failures:** Immutability is genuinely structural and I verified it on a live ledger: `UPDATE audit`/`DELETE FROM audit` both abort with 'audit is append-only', and because openLedger runs the migration ladder BEFORE exec'ing schema.sql (db.ts:279-291), the v7 rebuild that drops the audit table (db.ts:62-63, which also drops its triggers) gets them re-created on the same boot — a subtle ordering dependency that happens to be correct. The real gap is COMPLETENESS, not immutability: memory mutations write the row and the audit record as two separate autocommit statements, so a crash between them leaves an unaudited memory mutation. CLAUDE.md's own rule ("every state change goes through one transition function that writes tasks + audit atomically") is honored in tasks.ts and not in memory.ts. Secondary: memory_written's payload is only `{memoryId}` (memory.ts:82) — not tier — and memory_tier_changed records the new tier only (:135), so the audit alone cannot reconstruct at what standing a belief entered or what it was demoted from.
- **rung:** R5 for immutability; R2/R3 for completeness (convention, correct in tasks.ts, missed in memory.ts) → ceiling R5 for completeness · residual: mechanical
- **promotion:** Either wrap each memory mutation + its audit in db.transaction (matching tasks.ts's transition), or push it into the schema: AFTER INSERT / AFTER UPDATE triggers on memory_items that insert the audit row, so no code path can mutate memory without an audit record — the ledger-invariants-in-the-schema pattern CLAUDE.md already establishes. Include tier (and the prior tier) in the payload while touching it.
- **cost:** Near zero. The trigger route moves the payload shape into SQL, so the audit kinds and the JSON shape must stay in step with audit.ts's AuditKind union and the CHECK at schema.sql:145-148.
